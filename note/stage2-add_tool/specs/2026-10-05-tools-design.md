# 第二阶段设计：客服聊天中的单轮工具调用

日期：2026-10-05

状态：对话设计已获批；书面 spec 待用户审核。尚未开始产品实现。

## 1. 意图与已确认边界

用户要在现有客服聊天页中查询业务数据，由模型自行选择工具，最终答案仍通过 SSE 流式输出。本章学习重点是 Function Calling、工具执行与结果回灌，以及真实 MySQL 持久化。

用户关键原话：

- 「工具链要长在客服聊天本身，用户在聊天页问一句就能触发」。
- 「目前先只做单论限制」；已确认每条用户消息最多执行一个业务工具。
- 「邮费是多少…关键词查表查不出来——这个漏召回是预期结果」。

已批准：固定单工具流程与服务分层；四表及数据库上下文；错误处理、幂等重试、取消和验收设计。

技术固定为 Python、FastAPI、SQLAlchemy、Docker MySQL、LangChain `@tool`。模型仍直连 OpenAI 协议上游，地址、模型、密钥通过本地 `.env` 配置；当前为 DeepSeek / deepseek-flash。遇到所选技术或模型接口无法满足要求时停止并询问，不自行替换。

本章不做 Agent Loop、向量检索、RAG、真实电商或物流 API、订单/商品/物流表、登录系统、历史聊天列表与远端 CD。第一阶段未交付的结构化提取不隐式并入本章。

## 2. 架构与职责

采用独立聊天服务协调固定流程。相比直接把全部逻辑放进路由，分层便于独立验收、理解工具边界和后续扩展；不引入通用 Agent 框架。

- 路由层：校验 HTTP 请求、建立 SSE 响应、处理断开连接。
- 聊天服务：会话与轮次生命周期、上下文预算、选择工具、回灌、最终流式回答。
- 模型网关：工具选择调用和最终文本流；保留现有供应商设置与安全错误转换。
- 工具层：五个 `@tool`、明确的注册表、参数 Schema、执行期限与有限重试。
- 数据层：SQLAlchemy 模型、短事务、会话/消息/FAQ/工单访问与初始化数据。

工具注册表同时提供模型可见 Schema 与实际执行白名单，禁止根据模型输出动态导入或执行任意函数。会话、轮次和数据库访问由服务端注入，不作为模型可修改的工具参数。

## 3. 单轮调用协议

一次用户请求的顺序：

1. 校验输入，建立或读取会话，保存用户消息并标记本轮进行中。
2. 从数据库读取成功历史轮次，构造包含 System Prompt 与工具定义的选择请求。
3. 模型最多选择一个工具；无工具则走最终回答。选择阶段的草稿文本不作为最终回复展示。
4. 保存 assistant 工具申请，验证名称和参数，发送状态帧，执行已选工具。
5. 保存对应 tool 结果，构造匹配 `tool_call_id` 的 ToolMessage，回灌给模型。
6. 最终生成阶段禁止工具调用，真实接收上游文本增量并发送 `delta`。
7. 确认正常结束且最终答案落库后，标记本轮成功并发送 `done`。

每轮最多两次模型请求：一次选择，一次最终生成。没有工具时也直接进入关闭工具能力的最终生成，不用定时拆分完整字符串伪装流式。

模型一次申请多个工具时，执行零个业务工具，为各申请保存匹配的超限错误结果，再进入禁止工具的最终回答。未知名称、无效 JSON 或 Schema 错误不执行业务工具；有有效调用标识时回灌关联错误，无合法标识、不能构造有效协议时结束为明确错误，不发送损坏的对话给上游。

最终生成若仍返回工具申请，视为协议失败，不执行、不循环。工具参数校验通过不代表模型决策正确，真实场景验收需核对选择、参数、结果和答案。

## 4. 四张表与持久化

数据库只创建以下四张业务表。可增加支撑约束、排序、轮次状态和幂等的字段，但不增加其他业务表。

| 表 | 必需内容与约束 |
| --- | --- |
| faq | 主键、问题、答案、分类；固定演示种子 |
| conversations | 会话主键、演示用户标识、处理状态、创建时间 |
| messages | 主键、会话外键、role、内容、工具申请 JSON、tool_call_id、创建时间；轮次标识和状态用于完整轮次选择 |
| tickets | 工单号主键、会话外键、问题描述、工单类型、处理状态、创建时间 |

消息 role 仅允许 user / assistant / tool；System Prompt 不作为这些业务消息落库。assistant 工具申请可为空文本，但必须保留工具名称、参数与调用标识；tool 保存结构化结果与对应调用标识。

同一轮的用户消息、assistant 工具申请、tool 结果、最终 assistant 回复可追溯到同一轮次。错误或取消保留审计记录与已生成部分文本，但不标记为成功上下文。按稳定消息主键排序，不能仅依赖创建时间区分先后。

使用 UTC 时间、外键及会话/消息排序索引。每次数据库工作使用独立会话与短事务；不把事务或行锁贯穿模型等待和 SSE 流。不得并发共享同一 AsyncSession。

同一会话同时只允许一个进行中的请求，冲突返回 409；用数据库原子状态变更控制，不只靠单进程内存锁。异常退出留下的进行中轮次应有有限失效恢复，恢复时标记失败而非补成成功；过期执行者不得覆盖新轮次状态。

首次请求由后端生成 conversation_id；页面在当前聊天会话中持有并在后续发送。演示用户标识由服务端设定，本章不把此机制描述为用户鉴权或多租户隔离。

页面刷新开始新的聊天；旧记录仍在数据库，本章不提供恢复历史 UI。

## 5. 上下文与预算

数据库是多轮上下文的唯一来源。客户端不再提交聊天历史，不能注入 tool 消息或伪造成功查询。保留 `/chat/stream` 路径，请求改为 message 与可选 conversation_id；旧的非空 history 请求应明确拒绝，README 与演示命令同步更新。

继续第一阶段最简保守 token 估算与历史裁剪，不宣称精确计数。历史按完整成功轮次裁剪，assistant 工具申请及对应 tool 结果必须一起保留或移除。

选择和最终生成分别校验预算，计入工具 Schema、调用参数和结果内容，预留输出额度。工具结果设长度和条数上限；若当前消息、固定 Prompt 与本轮必需结果仍超预算，结束为明确错误，不删除结果后让模型猜测。

## 6. 五个工具

| 工具 | 模型输入 | 执行行为 |
| --- | --- | --- |
| query_order | 有边界的订单号字符串 | 工具内部随机生成演示订单数据，并返回请求的订单号 |
| query_product | 有边界的商品标识字符串 | 工具内部随机生成演示商品数据，并返回请求的标识 |
| query_logistics | 有边界的订单号字符串 | 工具内部随机生成演示物流数据，并返回请求的订单号 |
| query_faq | 有边界的关键词字符串 | 参数化 SQL LIKE 查询 faq，返回有限条目或明确未命中 |
| create_ticket | 问题描述、受约束的工单类型 | 使用服务端会话上下文写 tickets，返回真实工单号与状态 |

每个工具使用显式 Schema，拒绝额外字段。演示查询结果带演示标记，Prompt 要求不得将其描述为真实系统查询。随机结果在一次调用中生成并用于保存及回答；测试注入可控随机源验证内容，不在回答阶段重新生成。

FAQ 不做同义词、语义改写或备用知识回答。keyword 必须来自本条用户消息中的连续原文，并校验此约束；SQL 对 `%`、`_` 和转义字符作字面处理，采用绑定参数，不拼接 SQL。

FAQ 种子包含“退货政策”与“运费”条目，问题及答案不包含“邮费”。“退货政策是什么”应查询并命中；“邮费是多少”应执行 query_faq 后返回未命中，模型应说明未找到，不能自行替换成“运费”掩盖本章的预期漏召回。

种子覆盖四表的演示关联记录，初始化可重复运行而不重复插入，不污染真实浏览器验收的新会话。工单号码由服务端生成；工具不能指定任意会话或工单主键。

## 7. 执行错误、重试与取消

工具结果采用统一结构区分成功、未命中和失败。未命中是正常业务结果，不重试。未知工具、参数错误、模型多申请超限也不重试。

单次工具执行有期限，暂时性数据库/执行错误或超时最多重试一次，总执行时间有明确上限；具体默认值与配置项在实现计划中固定。重试只针对已选的同一次工具调用，不能重新请求模型选工具。

create_ticket 使用会话、轮次与 tool_call_id 推导稳定幂等工单号，并依赖主键约束。超时后先核对该工单是否已提交，重试必须复用同一号码；不能因“不知道是否写入”新建第二个号码。未保证幂等前不自动重试写操作。

工具失败回灌安全错误，模型不得编造查询成功或工单已创建。数据库连接、SQL、供应商原始异常、密钥不出现在公开 SSE；数据库无法保存结果时不能报告本轮成功。

前端中止或浏览器断开，取消传播到当前模型或工具任务，关闭流并记录取消；不得吞掉 CancelledError 后重试。已提交的工单保留，不声称取消撤销了数据库操作。取消/失败轮次不用于后续上下文。

## 8. SSE 与页面

继续支持 `delta`、`done`、`error`，增加会话信息与工具状态帧。会话信息在首个 delta 之前返回 conversation_id；工具执行前就发送运行状态，不等待最终文本才发送。

状态数据包含服务端选定的工具名、调用标识、阶段与必要的安全结果摘要。重试更新同一个徽章，不显示为模型再次选工具。徽章状态为运行、成功、未命中或失败；它必须来自真实后端事件，不能由页面猜测用户问题。

最终 `done` 仅在模型正常结束、存在有效文本且数据库成功提交后发送。流已建立后的失败使用 error 帧；流建立前的验证/会话冲突等仍用明确 HTTP 错误。空回复、截断、异常断流保留第一阶段失败行为。

保留谷鱼Y的客服助手、蓝色小鱼、纯黑主文字、绿色用户气泡与可取消方框。聊天页改造按用户授权的 Vibe Coding 进行，不套后端 brainstorm/TDD/code review；仍做真实浏览器体验验收。

## 9. 配置、Docker 与 CI

新增数据库和工具执行相关设置通过环境变量配置，敏感值只存本地忽略的 `.env`。公共配置示例和 README 用英文，不上传密钥。继续保留 DeepSeek thinking disabled 与已验证的 OpenAI Chat Completions 接入设置。

Docker Compose 起 MySQL 和应用；MySQL 使用固定版本、命名卷与健康检查，应用等待数据库可用。具体镜像版本、异步驱动及初始化命令在 Context7/官方文档核对后写入实现计划，不直接采用浮动 latest。

本章没有持续 schema 演进需求，使用显式开发初始化命令建表和幂等种子，不额外引入迁移框架；破坏性重置必须单独指令，不能启动时默认删表。

CI 保留现有离线检查，新增真实 MySQL 集成检查与应用镜像构建，CI 不依赖真实模型密钥。真实 DeepSeek 与浏览器场景在本机单独验收。状态分别报告：配置已提交、检查通过、本机部署已验证；远端 CD 未配置/未验证。

## 10. 验收证据

后端可单测代码走 TDD；Prompt 与演示种子使用标注样例验证。gpt-6-luna max 实现，主助手独立验收；效果不足时主助手可接手并记录原因。

必须覆盖：

1. 浏览器问“订单 1001 的物流到哪了”：实际选 query_logistics，参数订单号正确，气泡出现真实徽章，最终流式答案符合这次随机返回。
2. 浏览器问“退货政策是什么”：实际 SQL LIKE 命中，答案符合种子内容。
3. 浏览器问“邮费是多少”：实际执行 query_faq，验证原词参数与 SQL 零结果，回答未命中；作为预期漏召回记录，不记作功能失败。
4. 同会话追问接住上轮上下文；数据库包含正确配对的工具申请与结果，取消/失败轮次被排除。
5. 五个工具的 Schema、非法名称/参数、多个申请超限、未命中、超时重试上限、取消及工单幂等；没有第二轮工具选择。
6. 真实 MySQL 四表、外键、种子幂等、流水顺序、会话并发冲突与过期恢复、工单重复调用不重复写入。
7. curl 能看到会话信息、工具状态与真实文本 delta；本机 Docker 应用及 MySQL 实际启动并完成业务请求。
